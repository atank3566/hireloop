# routing — 구조 제공 여부로 A/B 결정

분기 기준은 "화면정의서냐 아니냐"가 **아니라** "데이터 구조 신호가 있느냐"다. 화면정의서는 구조 신호가 강한 입력의 한 종류일 뿐이고, 일반 요청도 같은 파이프라인을 탄다.

## 구조 신호란

입력에 다음 중 하나라도 명시되어 있으면 "구조 제공"이다:
- 필드 목록 (항목명 + 컨트롤/타입)
- 마스터-디테일 구분 (헤더 vs 반복 품목, "~별 목록")
- 키/조인 (마스터키, 디테일키, "주문번호로 상품 조회" 같은 부모-자식 관계)

## 두 경로

### 구조 제공 → 그대로 따른다 (보조정보는 병합)

- **제공된 데이터 구조 = 1차 진실.** 필드/키/카디널리티를 **임의로 바꾸거나 추가하지 않는다.**
- 화면정의서의 부가 정보(컨트롤 의도·기본값·버튼 동작·통제 로직)는 **보조로 병합**한다 — 구조를 덮어쓰지 않고 살을 붙이는 용도.
- 마스터-디테일(1:N)·반복 목록·선택지 데이터가 있으면 **B 경로(데이터연결)** 로 진화한다 → `data-connection.md`. 시나리오에 `DataConnection`+`Ckeys`+`intent.mock`.
- 단건 정적 표시뿐이면 굳이 데이터연결하지 않고 `Label` 로 (정적, A).

> "엑셀처럼 데이터 형식을 주는 경우" = 이 경로. 준 구조에 맞게 쓰고, 추가적인 건 보조로만.

### 구조 미제공 → 묻지 말고 추론 (지금처럼 생성)

- "재고 조회 화면 만들어줘" 처럼 구조가 없으면 **사용자에게 마스터-디테일·키를 묻지 않는다.**
- `conventions.md` + `templates/` 의 코퍼스 컨벤션을 근거로 마스터-디테일·키를 **알아서 추론·구성**한다.
- 반복/선택지 데이터가 자연스러운 화면(목록·조회·주문 등)이면 B, 단순 단건 표시 화면이면 정적 A.
- 추론한 마스터-디테일·키 구성은 **추론 가정으로 기록**(`spec-format.md` frontmatter `assumptions`)하고 keyRole 이 애매하면 `provisional`.
- **질문은 화면의 종류/목적이 정말 모호할 때만 최소로** 한다 (예: "재고"가 입출고인지 현황조회인지 한쪽으로도 못 좁힐 때). 키·필드·마스터-디테일 자체는 질문 대상이 아니라 추론 대상이다.
- **목업데이터를 반드시 추정해 세팅한다 (빈 화면 금지).** 구조가 없어도 도메인에 맞는 카테고리·필드·현실적 값을 **알아서** 만들어 채운다 — 기존 생성과 동일하게. 목록/반복(B)이면 시작 Step.Init 에 `intent.mock` 으로 3건+(부모-자식이면 부모 2~3 × 자식 2~3), 단건 표시(A)면 각 Label 에 현실적 `labeltext` 리터럴. 구체 추정 규칙은 `mockup.md`. 빈 리스트·빈 폼·placeholder 만 있는 화면으로 끝내지 말 것.

## 결정 요약

| 입력 | 경로 | 시나리오 산출 |
|---|---|---|
| 구조 제공 + 마스터-디테일/반복/선택지 | **B** | DataConnection + Ckeys + intent.mock |
| 구조 제공 + 단건 정적 표시 | A | Label.labeltext |
| 구조 미제공 + 목록/조회성 | **B**(추론) | DataConnection + intent.mock (가정 기록) |
| 구조 미제공 + 단순 표시성 | A(추론) | Label (가정 기록) |

A/B 는 한 화면 안에서 **혼재**할 수 있다 — 헤더·요약은 정적 Label, 반복 목록·선택지는 B. 노드별로 판정한다(SKILL.md "데이터 표시 결정" 과 동일 기준).

> **공통**: 구조 제공이든 미제공이든, 화면은 항상 목업데이터로 채워 "살아있는" 프로토타입이어야 한다. 미제공이라고 비워두지 않는다 — 추정해서 채우는 게 기본값이다 (`mockup.md`).
